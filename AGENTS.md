# НПП «Импульсные технологии» — корпоративный сайт

## Цель
Современный high-tech корпоративный сайт производителя сильноточной / высоковольтной модуляторной техники. Админ-редактируемый контент, блочная сборка страниц, мультиязычность (ru/en, раздельные домены), SEO-управление.

## Стек
- **Backend**: Laravel 13.29, PHP 8.5.4, MySQL (БД `imp-tech`, user/pass `imp-tech`), Livewire v4.4.3, Orchid 14.53 (админка)
- **Frontend**: Blade, Tailwind v4, Vite 7, GSAP 3.15, Lenis, AOS, Three.js 0.185
- Модули PHP: `intl`, `pdo_mysql`

## Окружение (Windows / PowerShell 5.1)
- Shell: PowerShell. Блокирует `.ps1`. Использовать `npm.cmd` (не `npm`).
- Проект: `C:/OSPanel/home/imp-tech.local` (OSPanel).
- Тестовый сервер: `http://127.0.0.1:8099`.
- Страницы-заглушки / буфер для временных файлов: `C:\OSPanel\temp\PHP-8.5\default\opencode`.
- Не использовать focus tool (его нет), искать/читать/править файлы узкоспециально, избегать вывода `node_modules`.

## Чтение / поиск файлов и вывод команд (важно)
- НЕ читать, НЕ искать (grep/glob) и НЕ листинть целиком содержимое: `node_modules/`, `vendor/`, `storage/`, `.git/`, `public/build/`, `.cache/`, `.idea/`.
- Поиск файлов/строк вести только по целевым папкам: `app/`, `resources/`, `routes/`, `database/`, `config/`, `public/`, `tests/`, `bootstrap/`.
- В bash НЕ запускать рекурсивный листинг корня проекта (например `Get-ChildItem -Recurse` в корне — вызывает шум из node_modules). Вместо этого: указывать `workdir` в нужную папку, фильтровать `-Filter`/по расширению, либо использовать `rg` с явным `--glob '!node_modules'` / `--glob '!vendor'`.
- Избегать вывода содержимого `node_modules`/`vendor` в любой команде.

## Архитектура / ключевые решения
- **Мультиязычность — «Localized URL helper»**: один набор маршрутов + авто-префикс `/en`. Глобальный middleware `SetLocaleFromDomain` (в `bootstrap/app.php` через `$middleware->append`) снимает `/en` с пути до роутинга. Хелперы в `app/Support/helpers.php` (autoload `files` в composer.json): `locale_path()`, `localized_route()`, `locale_alternate()`.
- **Транслитерация**: колонки `*_ru` / `*_en` (без spatie). `app/Models/Concerns/HasTranslatableAttributes.php`, `HasSlug.php`.
- **URL-построение**: `app/Models/MenuItem.php`, `Page.php`, `Product.php` используют `locale_path()`. hreflang-альтернативы — `app/Services/SeoPresenter.php` (`hreflangUrls()`/`urlForLocale()`).
- **Контент/блоки**: `app/Services/BlockRenderer.php`, `SiteSettings.php`, `ImageHelper.php`; представления `resources/views/pages/*.blade.php`, `blocks/*.blade.php`, `layouts/partials/{seo,header,footer}.blade.php`.
- **Главная**: WebGL-частицы (Three.js), GSAP/Lenis/AOS, тёмная тема (ink-950) + неоновый акцент/gradient. `@tailwindcss/typography` подключён через `@plugin` в `resources/css/app.css`.
- **Vite**: ручной сплит `three` через `build.rollupOptions.output.manualChunks` в `vite.config.js` (главный JS 693KB→188KB). Фавиконка `public/favicon.svg`.

## Конвенции по коду
- Blade-директивы `@context`/`@type` конфликтуют с Blade — экранировать как `@@context`/`@@type`.
- `@@` — лишний слой не нужен, только там где Blader конфликтует.
- View composer для `$siteMenu` — в `AppServiceProvider`.

### Грабли Orchid (важно для будущих правок)
- **Quill (WYSIWYG)**: `Orchid\Screen\Fields\Quill::make('model.field')->base64(true)->height('320px')->toolbar([...])`. Отдаёт HTML-строку, идентично TextArea — save-экраны менять не нужно. `base64(true)` встраивает картинки прямо в HTML (просто, но «тяжелит» запись); без `base64` картинки требуют Attach/upload. Для больших полей (body/description) height 400px/320px.
- **Локализация значений настроек**: НЕ использовать `SiteSettings::localized($key)` — он строит ключ `key.ru` (точка), а хранятся локализуемые значения как `key_ru`/`key_en` (как у сущностей). Выбирать напрямую `siteSettings->get('brand.tagline_'.app()->getLocale())` с fallback, а `Setting::set('brand.tagline_ru', ...)` хранит group='brand', key='tagline_ru'.
- **CSRF Orchid для POST-тестов**: токен приходит в `<input name="_token" value="...">` на странице (login и edit), а НЕ только в meta. Для save после логина делать повторный GET edit-страницы, чтобы взять актуальный `_token` из формы (иначе 419). Login: GET `/admin/login` → взять `_token` → POST логин → GET target page → `_token` → POST `{current_url}/save`. (Обновлено: ранее считалось что токен только в meta — теперь в input.)
- **Список-экраны**: НЕ использовать `Layout::table(X::class)` (в Orchid 14 `Layout::table()` требует 2 аргумента — title+layouts → `ArgumentCountError`). Возвращать класс layout прямо в массиве `layout()`: `return [ XxxListLayout::class ];` (как в стоковом `UserListScreen`).
- **Модели в таблицах Orchid обязаны иметь `getContent()`** (иначе 500 `Call to undefined method ...::getContent()`). Добавлять трейт `Orchid\Screen\AsSource` во все модели, отображаемые в админ-таблицах (Product, ProductFamily, Page, Post, CaseStudy, Application, Menu, MenuItem, Lead, Block).
- **`Select::fromModel($model, $name, $key)`** — 3-й аргумент это `?string $key` (колонка значения), НЕ Closure. Для скоупа запроса использовать `->fromQuery(Builder, $name)` (см. `MenuItemEditLayout`).
- **Ссылки на вложенные create-маршруты с моделью** (`blocks.create`/`items.create`) при построении URL кидают `Missing required parameter`, даже если скрыты `canSee(false)`. Параметр подставлять с дефолтом: `->route('platform.content.pages.blocks.create', $this->page->id ?? 0)`.
- **`view()`** в классе Screen конфликтует с базовым `Screen::view()` → переименовывать (в `LeadListScreen` → `viewLead`).
- **Вкладки не обязательно через экран**: можно превратить сам EditLayout в `extends Orchid\Screen\Layouts\Tabs`, задав в конструкторе `$this->layouts = ['Русский'=>RuLayout::class, ...]` (принимаются и объекты, и класс-строки) — тогда экраны (`Layout::block(XxxEditLayout::class)`) не трогаются. `Layout::tabs([...])` тоже можно вкладывать в `Layout::block(...)` (`block` принимает `Arr::wrap`).
- **SEO `$seo` в шапке**: анонимный компонент `<x-layouts.app>` НЕ прокидывает переменные родительского view, поэтому `$seo` не доходил до `layouts/partials/seo.blade.php`. Решение — глобальный `View::composer('*')` в `AppServiceProvider` подкладывает `$seo`: из контейнера `app()->instance(SeoPresenter::class, ...)` (его регистрирует `Controller::seoFor()`), иначе fallback. Проверять/записывать только если `seo` отсутствует или null: `! ($view->offsetExists('seo') && $view->offsetGet('seo'))`.
- **Boolean чекбоксы обязаны иметь `->sendTrueOrFalse()`**: без него Orchid рендерит `<input type="checkbox" value="value">` и при галочке в INT-колонку уходит строка `'value'` → `SQLSTATE[HY000] 1366` на MySQL 8 strict. С `sendTrueOrFalse()` — скрытый `value=0` + чекбокс `yesvalue="1"` → всегда валидный `0/1`. ВАЖНО для ЛЮБОГО нового boolean-поля в админке.
- **`$this->item` не доступен в `save()` на create-POST**: Orchid не гидратирует публичные свойства из `query()` при методе save — обращаться к `$this->item->...` нельзя. Для параметра из URL (напр. `menu_id`) брать из роута: `$request->route('menu')` (см. `MenuItemEditScreen::save()`).
- **Эмуляция браузера для POST-тестов Orchid**: нужен cookie jar + CSRF (токен берём из `<input name="_token">` страницы — см. граблю CSRF выше). Кнопки `Button::method('save')` отправляют POST на `{current_url}/{method}` (напр. `/content/products/create/save`), а НЕ `method` в теле — см. `vendor/orchid/platform/src/Screen/Actions/Button.php:94`. Для проверки payload-полей в `save()` вводится временный `Log::debug(...)`.
- **JSON-колонки image/icon + `Picture`-поле**: колонки `..._image`/`icon` типа JSON, `Picture` (одиночная картинка) ожидает строку. Решение: cast `'array'` в модели, а в `save()` нормализовать значение в **одиночную строку** (массив → первый элемент; JSON-строка → декод). Eloquent-writer cast'a array сам json_encode-ит строку в `"/storage/path"` (валидный JSON) → БД принимает, на чтении декодирует в строку → Picture/фронт работают. НЕ сохранять в JSON-колонку голую строку/массив напрямую (MySQL JSON требует валидный JSON-текст).
- **PowerShell + `php -r`**: экранировать `$` как `` `$ `` внутри двойных кавычек; не называть переменные `$app`/`$kernel` при переопределениях Laravel-контейнера в однострочниках (конфликт). Для многострочных тестов удобнее временные `.php`-скрипты в `C:\OSPanel\temp\PHP-8.5\default\opencode`.
- **BlockRenderer не прокидывает переменные родительского view в блоки**: `render()` создаёт собственный `view(...)`-скоуп, поэтому любые переменные, переданные в `pages/home.blade.php` (напр. `$products`), НЕ видны внутри `blocks/*.blade.php` (там `?? collect()` → пусто → фолбэки «No ... yet.»). Прокидывать явно 2-м аргументом `render($block, ['products'=>...])`; внутри блока держать `$products ?? collect()`.
- **Upload/Picture загрузка файлов в админке требует permissions `platform.systems.attachment`**: все поля `Upload`/`Picture`/`Attach` грузят файлы через vendor `AttachmentController::upload()`, конструктор которого (`AttachmentController.php:33`) вызывает `checkPermission('platform.systems.attachment')` и без этого права отдаёт **403 → JS показывает общую «ошибку валидации», игнорируя файл/размер/расширение** (пофикшена причина «перепробовал файлы — ни одно не загрузилось» по всей админке). Право добавлять в `AdminSeeder::$permissions` (ДОБАВЛЕНО) И точечно в существующие роль `admin` + пользователя (обычный `db:seed` с `firstOrCreate` НЕ раскатывает новые ключи на уже посеянную роль — править `permissions`-JSON напрямую). Сам upload-эндпоинт — POST на `admin/systems/files` (с `_token` + `storage=local` + файл), НЕ на `files/{storage}` (там только GET/HEAD/DELETE → 405).
- **`Upload` (multi) хранит в БД ID вложений, `Picture` (single) — строку `/storage/...`**: поле `Upload` отправляет на submit массив **ID attachment** (рендер грузит модели по `id` — `vendor/.../Fields/Upload.php:117`), а `Picture` с дефолтным `target='url'` — относительный URL. Поэтому фронту для `Upload`-галереи нельзя слать значение напрямую в `<img>`: резолвить через `ImageHelper::url()` (в нём теперь `Attachment::find(id)->url()` для целых/числовых). Также `Attachment::url()` и `Storage::disk('public')->url()` возвращают absolute на основе `APP_URL` — если сайт крутится на другом хосте (`127.0.0.1:8099`), такие URL надо вести к `/storage/...` (это делает `ImageHelper::resolvePath()`).
- **Диск загрузки Upload: дефолт — `public` (config `platform.attachment.disk`), а НЕ local**: real-поле Upload в админке грузит на public → файл доступен по `/storage/...`. Если в ручном POST-тесте слать `storage=local` (как в старой записи ниже про 403 прав), файл ляжет на непубличный диск `storage/app` и GET `/storage/...` отдаст **403**. Поэтому при ручной эмуляции загрузки (`POST admin/systems/files`) НЕ передавать `storage` вообще (взяётся дефолт public) — вложения будут отдаваться с фронта.
- **Upload-поле может «записать» JS-мусор `"undefined"` в JSON-колонку** (напр. `products.gallery = ["undefined"]` — при удалении/перетаскивании файла в админке save проходит): `null`/`''` — не единственный хлам. Старые `normalizeGallery()` и `ImageHelper::url()` с ним справлялись (сохраняли `/storage/undefined` / absolute-URL). Теперь: `ProductEditScreen::normalizeGallery()` отбрасывает `['undefined','null','false','NaN','[object Object]']`, `ImageHelper::url()` для таких строк и строк, не начинающихся со `/`, возвращает fallback/null. При починке «пропавшей» картинки: `UPDATE products SET gallery='["/storage/import/<family>.svg"]' WHERE id=...` — файл заглушки проверять `Test-Path public/storage/import/...`. Вёрстка галереи в `pages/product.blade.php` рендерит `src` через `json_encode` → в HTML слэши заэкранированы (`\/storage\/...`) — это НОРМА, не баг.
- **`Matrix` (repeater) и удобные формы вместо сырого JSON**: **НИКОГДА `->keyValue(true)` для повторяемых строк** — он рендерит имена без индекса строки (`field{Ключ}`/`field{Значение}`), все добавленные строки схлопываются в одну пару в POST → ничего не сохраняется. Для списков строк использовать не-keyValue (default): **`columns()` задавать «перевёрнуто»: `['РусскаяМетка' => 'fieldKey', ...]`** — так шапка таблицы остаётся русской, а в POST уходят корректные имена `name[i][fieldKey]` (повторение поля по типу можно задавать через один и тот же `Matrix::make('name')` с разными `columns`, показывая один за раз через фильтрацию `fields()`). `fields()` ключевать по `fieldKey`. На `save()` `name[i][col]` даёт массив ассоциативных массивов/списков — собирать построчно в нумерованный массив (`block.content_stats`/`content_items`/`points`/`images`), а `specifications` — в список `[{name,value}]`. Условный показ поля по типу модели — не `canSee()`, а фильтрацией в `fields()` (`array_filter`): `BlockEditLayout::row($field, [types])` возвращает `null`/поле и строится `blockType()` из `$this->query['block']->type` (Query — это `Repository` c `ArrayAccess`; при `$this->query` null отдавать дефолт). Служебные поля вида `content_*`/`*_rows` НЕ должны попадать в `fill()` на save — их `unset($data[$field])` обязателен, иначе Eloquent будет писать несуществующие атрибуты. Всё это — только способ ввода: схему БД и формат `content`/`specifications` не менять.
- **Локализация блоков и характеристик (ru/en) — формат хранения в JSON**: `blocks.content = ['ru'=>{все поля}, 'en'=>{все поля}]` (полное вложение: и текстовые, и нетекстовые поля дублируются в обе ветки); `products.specifications = [{name_ru, value_ru, name_en, value_en}, ...]`. Ввод в админке — вкладки Ru/En/Общие (единообразно с Post/Product/ProductFamily): `BlockEditLayout extends Tabs` с `BlockEditRuLayout`/`BlockEditEnLayout`/`BlockEditCommonLayout` (трейт `BlockEditFields` — фильтрация полей по `block.type` и группам stats/items/points/images), у Product спецификации — две Matrix `product.specifications_ru_rows`/`product.specifications_en_rows` (в Ru/En вкладках), в Common — только family/code/gallery/sort/is_active. `BlockRenderer::render()` выбирает ветку по `app()->getLocale()` с фолбэком `config('locale.default','ru')` (в `render()`: если `content` имеет `ru`/`en` → `localizedContent()`). Фронт `product.blade.php` читает `$spec['name_'.app()->getLocale()] ?? $spec['name_ru']` (фолбэк `_ru`). `ProductEditScreen` хранит/читает через `specsToRows($specs,$locale)`/`rowsToSpecs($ruRows,$enRows)`.
- **`->title()` во вложенных `Input::make()` внутри Matrix рендерит `<label class="form-label">` в каждой ячейке** + дублирование с шапкой таблицы. Использовать `->placeholder()` для подписей полей внутри `fields([...])` Matrix (внешние `->title()` самой Matrix — ок).
- **`BlockRenderer::localizedContent()` — пофайловый fallback из ветки локали по умолчанию**: если ветка текущей локали есть, но её ключ пуст (`null`/`''`/`[]`) или отсутствует, значение берётся из `content.{default}` (обычно ru). Это комбинация «ветка целиком» + «пер-поле fallback» — список-поля (`items`/`images`/`points`) не мёржатся (нет дублей), в EN-ветке с пустым `title`/`body` показывается русский текст.
- **В save()-экранах НЕ `unset` реальные колонки модели**: `BlockEditScreen::save()` выбрасывал `type/sort/is_active/page_id` из `$data` (их считали служебными) → на create уходил `INSERT` без `type` → `SQLSTATE[HY000] 1364 Field 'type' doesn't have a default value` (MySQL 8 strict). `unset`-ить ТОЛЬКО служебные ключи (`content_*`, `*_rows`), а `type/sort/is_active` нормализовывать и сохранять (`type` дефолт `'text'`, `sort` → int, `is_active` → bool из `sendTrueOrFalse`; `page_id` берётся из `$request->route('page')`). Отдельно: перед `pruneGroups()` задавать `$block->type` из формы — на create свежий route-binding экземпляр не имеет type, иначе не-текстовые блоки (gallery/features/…) теряли свои группы контента.

### Грабли фронта / сборки / верификации (важно)
- **Inline-форма `@php(...)` в blade кладёт PHP-фейтал** (в т.ч. через Livewire `ExtendedCompilerEngine`): `@php($x = $x ?? collect())` компилируется в `<?php($x ...` без пробела/`?>` → `syntax error, unexpected token "@"` на регенерированном view. Использовать ТОЛЬКО блочную форму `@php ... @endphp`.
- **Arbitrary Tailwind-классы (`pt-[…]`, `z-[5]`, `h-[…]`) НЕ попадают в собранный CSS без пересборки**: после правки blade с такими классами обязательно `npm.cmd run build`, иначе правка «не работает» (выглядит как отсутствие пульса/эффекта). Актуальная сборка — `public/build/assets/app-taw_tg0D.css`.
- **Глобальный резерв под фиксированную шапку — `<main class="relative pt-18">` в `layouts/app.blade.php:31`** (72px; шапка `h-18` = 72px + 1px border ≈ 73px). Любые отступы hero-секции прибавляются ПОВЕРХ него — при расчёте вертикали логотипа помнить: факт. верх логотипа ≈ y93 = 73px (шапка) + 12px (полоса `pt-3`) ≈ зазор ~20px от низа шапки.
- **Контент hero**: секция `flex flex-col`; контент-блок обязан иметь `flex-col` (`flex-1 flex flex-col items-center justify-center`) — иначе бейдж/H1/описание/CTA ложатся в одну строку.
- **Проверка вёрстки без ручного браузера (работает и в plan mode)**: headless Chrome — `& 'C:\Program Files\Google\Chrome\Application\chrome.exe' --headless=new --disable-gpu --hide-scrollbars --user-data-dir=... --window-size=1280,800 --screenshot=... --virtual-time-budget=3000 http://127.0.0.1:8099/` + попиксельный анализ PHP из here-string (`@'...'@ | php`, без записи файлов). Классификатор «это логотип»: теал-голубые пиксели слева (b > 120, b − r > 60, g > 90); CTA — в x ≈ 1000..1280. Скриншоты/профиль — в `C:\OSPanel\temp\PHP-8.5\default\opencode\`.
- **OSPanel отдаёт 403 на отсутствующий файл в `public/storage`** (а не 404): при «сломанной» картинке проверять и БД, и реальное имя/расширение файла на диске (пример: в сидере `security.jpeg`, а загружен `security.png` → 403 в браузере).
